Vigil · Atelier

Worktrees — start fast,
leave clean.

A lightweight spec for creating, tracking, and removing git worktrees across multiple directories — with Vigil as the cleanup surface.

The problem

Running five Claude sessions in one repo is fine until you want them working on truly isolated branches at the same time. Git worktrees solve the isolation problem. What they don't solve is the bookkeeping.

Worktrees accumulate. You create one for a feature, another to investigate a bug, a third to prototype something. Each gets its own Claude session, its own branch. When the work is done you need to remove the directory, delete the branch, and maybe clean up any session artifacts — three steps that are easy to forget and annoying to look up. The last thing you want when you finish a task is a scavenger hunt.

This spec covers a small tool that handles the full worktree lifecycle: create with one command, track automatically via Vigil, remove with one keypress when the session goes Done.

Lifecycle

create → develop → merge / abandon → remove atelier wt new feature-auth ← one command: worktree + branch + launch ... work happens ... git push && gh pr create ← normal git flow, nothing special ... pr merges ... vigil → select Done session → R ← remove: directory + branch in one step

The create step is one command. The remove step is one keypress from Vigil, available whenever the session reaches Done. Between those two ends, nothing changes about how you work.

Create

A new atelier wt new command (or atelier worktree new) does three things atomically:

  1. Runs git worktree add <path> -b <branch> from the current repo root.
  2. Records the worktree in Atelier's registry (~/.vigil/worktrees.json), including which agent to use.
  3. Launches the chosen agent inside the new worktree directory using its AgentAdapter::attach_command().
# Usage
atelier wt new <name> [--agent <agent>] [--repo <path>] [--dir <path>] [--no-launch]

# Agents: claude (default), codex, pi, opencode — any adapter built into Vigil

atelier wt new feature-auth
# → worktree at ~/.vigil/worktrees/feature-auth
# → branch: feature-auth
# → launches claude (default agent)

atelier wt new feature-auth --agent pi
# → same worktree, launches pi instead

atelier wt new hotfix-login --agent codex --repo ~/code/myapp --dir ~/scratch/hotfix-login
# → explicit path, launches codex

Agent selection

The --agent flag accepts any agent that has a Vigil adapter: claude, codex, pi, opencode. The default is claude. Atelier does not know how to launch agents itself — it delegates to AgentAdapter::attach_command(), which each adapter already implements for session resumption. For a fresh worktree with no existing session, the adapter's launch command is used instead (a separate method, launch_command(working_dir), described below).

Any agent that has a Vigil adapter can be used. Adding a new agent to Vigil automatically makes it available here — no worktree-specific code needed.

Default path resolution

When --dir is omitted, the worktree lands at ~/.vigil/worktrees/<name>. All Vigil-owned worktrees share one root, regardless of which repo they came from. This means everything Vigil created is always in one place — ls ~/.vigil/worktrees/ is the complete picture, no per-repo hunting.

When --repo is omitted, Atelier infers the repo root from the current working directory using git rev-parse --show-toplevel. If the CWD isn't in a git repo, it errors immediately rather than silently creating something broken.

Branch naming

Branch name defaults to <name> exactly as given. Atelier does no automatic sanitization — the user controls the name. If the branch already exists, git worktree add will error; Atelier surfaces that error directly without wrapping it.

The registry

After a successful git worktree add, Atelier appends one entry to ~/.vigil/worktrees.json:

{
  "id":           "feature-auth",
  "agent":        "claude",
  "repo_root":    "/Users/ezeugo/code/myapp",
  "worktree_path":"/Users/ezeugo/.vigil/worktrees/feature-auth",
  "branch":       "feature-auth",
  "created_at":   "2026-05-17T14:00:00Z"
}

The registry is append-only on create; remove deletes the entry. Nothing else writes to it. If the file is missing or unparseable, atelier wt list treats it as empty and atelier wt new creates it.

List

atelier wt list
NAME AGENT BRANCH REPO PATH STATE feature-auth claude feature-auth ~/code/myapp ~/.vigil/worktrees/feature-auth exists hotfix-login codex hotfix-login ~/code/myapp ~/.vigil/worktrees/hotfix-login exists old-experiment pi old-experiment ~/code/myapp ~/.vigil/worktrees/old-experiment directory missing

list reads the registry, then verifies each entry by checking whether the worktree path still exists on disk. A missing directory is flagged as stale — the worktree was probably removed manually or by another tool. Stale entries can be pruned with atelier wt prune, which just removes them from the registry without touching git (since the directory is already gone).

Remove

Removal is either a CLI command or a keypress from Vigil.

CLI

atelier wt remove <name>

Runs three steps in order, stopping on the first failure:

  1. git worktree remove <path> — removes the directory. Git refuses if there are uncommitted changes; Atelier surfaces the refusal and stops. Add --force to override.
  2. git branch -d <branch> — deletes the branch. Git refuses if the branch isn't fully merged; Atelier surfaces the refusal and stops. Add --force to use -D instead.
  3. Remove the entry from the registry.
Safety by default. The two-step refusal (uncommitted changes, unmerged branch) is intentional. atelier wt remove without --force should never silently destroy work. The friction is the feature.

From Vigil

When a session's project_dir matches a path in the Atelier worktree registry, Vigil marks it with a small [w] indicator in the state column. When that session reaches Done, pressing R (capital R, distinct from anything else) triggers a two-line confirmation overlay:

session feature-auth · ~/code/myapp/.claude/worktrees/feature-auth Remove worktree? branch: feature-auth y remove directory + delete branch n cancel

On y, Vigil calls the same logic as atelier wt remove. If git refuses (uncommitted changes or unmerged branch), Vigil shows the error inline and returns to the session list without removing anything. The user can then attach (↵) to handle the git state and retry.

R is only available when:

  • The session is in Done or Idle state (not Running or AwaitingInput).
  • The session's project_dir is in the Atelier registry.

Sessions not in the registry, and sessions that are still active, do not show the R binding in the footer.

Vigil integration details

Registry read

Vigil reads the worktree registry once at startup and re-reads it after any R action. It does not watch the registry file for changes — a new atelier wt new in another terminal will show up on the next Vigil restart or after the next R round-trip. This is fine; worktrees are created infrequently.

The [w] indicator

A single character added to the right of the state label when the session is a registered worktree. It is the same dim color as the state column text — not alarming, just informational. The indicator disappears once the worktree is removed from the registry.

STATE PROJECT done [w] ~/.vigil/worktrees/feature-auth running ~/code/myapp awaiting ~/code/other-project

Creating a worktree from Vigil

Going to the terminal to run atelier wt new is friction. If you're already looking at a session in Vigil and want to spin up a new worktree for the same repo, you shouldn't need to leave. Pressing W on any session opens a small creation overlay:

New worktree · repo: ~/code/myapp name feature-auth_ agent claude codex pi opencode ↑↓ / tab to cycle ↵ create and launch ⎋ cancel

The repo is pre-filled from the selected session's project_dir, resolved to its git root. The user types a name, optionally cycles the agent with Tab, and presses ↵. Vigil calls the same create() path as the CLI — git worktree add, registry append, launch — then reloads the session list. The new session will appear on the next refresh tick.

W is available on any session that has a known project_dir inside a git repo. Sessions with no project dir (sub-sessions, orphaned logs) do not show the binding.

Footer

The footer adapts to the selected session. W is always shown when applicable. R is only shown for Done/Idle worktree sessions.

↑↓ jk navigate ↵ attach d dismiss u undo W new worktree R remove worktree q quit

Data model

FieldTypeNotes
idStringThe name given to atelier wt new. Unique within the registry. Used as the lookup key.
agentAgentKindWhich agent to launch in this worktree. Must have a Vigil adapter. Defaults to claude. Stored so atelier wt open can re-launch the right agent without flags.
repo_rootPathBufAbsolute path to the git repo. Used as the CWD for git worktree remove and git branch -d.
worktree_pathPathBufAbsolute path to the worktree directory. Matched against session project_dir in Vigil.
branchStringBranch name to delete on remove.
created_atDateTime<Utc>For display in atelier wt list.

Crate layout

atelier/
├── Cargo.toml                    # workspace
└── crates/
    ├── atelier-worktree/         # registry, create, remove, prune logic
    │   └── src/
    │       ├── lib.rs
    │       ├── registry.rs       # read/write worktrees.json
    │       ├── create.rs         # git worktree add + registry append
    │       └── remove.rs         # git worktree remove + branch delete + registry drop
    └── atelier-cli/              # thin main, subcommands
        └── src/
            └── main.rs           # wt new / wt list / wt remove / wt prune

atelier-worktree is a library crate with no async — git is called via std::process::Command, the registry is plain JSON on disk. Vigil links against it to read the registry and call remove().

AgentAdapter extension

The existing AgentAdapter trait already has attach_command(id) for resuming a session. Worktree launch needs one new method:

fn launch_command(&self, working_dir: &Path) -> Command;
// Claude:   `claude` (no flags) run from working_dir
// Codex:    `codex` run from working_dir
// Pi:       `pi` run from working_dir
// OpenCode: `opencode` run from working_dir

Each adapter implements it. atelier wt new calls it; atelier wt open (re-launch without recreating the worktree) also calls it. No adapter needs to know it's being called from a worktree — it just launches in the given directory.

Edge cases

Worktree directory was deleted manually

The registry has an entry but the path doesn't exist. git worktree list would also show it as stale. On atelier wt remove: skip the git worktree remove step (nothing to delete), still run git branch -d, then drop the registry entry. atelier wt prune handles all stale entries at once.

Branch was already deleted

On git branch -d failure with "branch not found": treat as success — the user already cleaned it up. Drop the registry entry and move on.

Session in a worktree is still Running

Vigil does not show R for Running or AwaitingInput sessions. The CLI atelier wt remove will still attempt removal — git worktree remove will refuse because the directory is in use. The refusal surfaces to the user without Atelier doing anything destructive.

Multiple sessions from the same worktree

The registry matches on worktree_path, not on session ID. If two sessions both have project_dir = worktree_path, both show [w]. Either session can trigger removal. Once removal succeeds, the path no longer matches and the other session loses its [w] indicator on the next refresh.

Worktree created outside of Atelier

Vigil only shows R for paths in the Atelier registry. A worktree created with raw git worktree add will not appear in the registry — Vigil treats it as a normal session. The user can add it to the registry manually with a future atelier wt import <path> command, or just remove it with git directly.

What is not in scope

  • Auto-remove on Done. Vigil never removes a worktree without explicit user confirmation. Session → Done does not trigger anything automatically.
  • Push / PR creation. Out of scope. Atelier creates and removes. Everything in between is normal git.
  • Non-git projects. Worktrees are a git concept. No equivalent is planned for non-git directories.
  • Remote repos. atelier wt new works on local repos only. Cloning first is the user's responsibility.
  • Worktree renaming. Not supported. Remove and re-create.

Implementation order

  1. atelier-worktree crate: registry read/write, create(), remove().
  2. AgentAdapter: add launch_command(working_dir) to the trait; implement for each adapter.
  3. atelier-cli binary: wt new, wt list, wt remove, wt prune. Validate end-to-end with real repos before touching Vigil.
  4. Vigil: read the registry at startup, match against project_dir, show [w] indicator.
  5. Vigil: R keybinding, confirmation overlay, call remove(), show inline error on failure.
  6. Vigil: W keybinding, creation overlay with name input and agent selector, call create().
  7. Vigil: conditional footer — W shown when session has a git repo; R shown for Done/Idle worktree sessions only.
