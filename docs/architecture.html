Vigil

One quiet watcher
for every coding agent.

A native terminal dashboard that watches your Claude Code, Codex, Pi, OpenCode (and the next one) sessions in parallel — and tells you which one needs you right now.

The premise

Agents wait on you more than you wait on them. The bottleneck is no longer model speed — it's human attention routing. When five sessions are running, four are idle and one is blocked on a permission prompt you can't see, you lose minutes per context switch and hours per day.

Vigil makes the fleet legible. It reads every running agent's session log, classifies what state each is in, and surfaces only the ones that need a human. You attend, you dismiss, you move on.

Design principles

  • The session log is the agent's, not ours. Vigil never writes to session files — it only reads them. When you send a message inline, Vigil pipes input into the agent's own stdin; the agent is what records the resulting line into its log. Vigil observes; the agent owns.
  • Agent-agnostic core. The UI never knows what kind of agent it is rendering. Adapters translate. The core (and therefore the TUI) is written exactly once.
  • State-driven UI. Every screen is a pure function of an AppState — no I/O, no globals, no hidden state. Rendering can be invoked outside the app loop, which makes the whole UI testable in isolation. Behavior lives in event handling; pixels live in render. The two are separate concerns by construction.
  • Local first. Everything lives on disk. No daemon, no server, no auth. v1 is one binary.
  • Uncertainty is first-class. Vigil itself doesn't know what state a session is in — the adapter does, and adapters can return Unknown when their heuristics aren't confident. The UI surfaces that explicitly. No confidently-wrong guesses.

Architecture

Three layers, one rule of flow: sources → adapters → core → UI. Every concrete agent lives in its own adapter crate; adding a new one is a trait impl plus a Cargo line.

The AgentAdapter trait

This is the single seam between Vigil and the world. Each backend implements it.

pub trait AgentAdapter: Send + Sync {
    fn kind(&self) -> AgentKind;
    fn roots(&self) -> Vec<PathBuf>;      // dirs to scan + watch

    async fn discover(&self) -> Result<Vec<SessionId>>;
    async fn read(&self, id: &SessionId) -> Result<Session>;

    // Pure: given the latest log + filesystem signals, what state is this in?
    fn classify(&self, log: &SessionLog, fs: &FsSignals) -> SessionState;

    // How to drop the user back into this session.
    fn attach_command(&self, id: &SessionId) -> Command;
}

Notice classify is pure. Watching the filesystem and shuttling events is vigil-core's job; deciding what an agent's quiescence means is the adapter's. Each agent encodes its own truth.

The state model

One enum, ruthlessly small. If two states would behave identically in the UI, they're one state.

StateMeansHeuristic (Claude Code)
RunningModel or tool actively producing output.JSONL written within last ~3s, no terminal user-turn yet.
AwaitingInputBlocked on a human (permission prompt, question, tool approval).Last entry is an unanswered tool_use needing approval, or assistant text ending on a question, no writes >5s.
IdleQuiet, no obvious ask, but the agent is still alive.No writes >30s, last entry is assistant text without a question pattern, and a live claude process still has the session file open.
DoneThe agent has detached from this session.No claude process holds the session file (checked via lsof-style probe), or the session file's last line is a known terminator.
ErrorCrash / unrecoverable adapter parse failure.Tool error block in last turn, or adapter raised.
UnknownThe adapter can't tell. Show as-is; don't guess.Default when no rule fires confidently.

The Idle / Done line is the hardest call in this model, and it's per-adapter. From a log file alone, "quiet for 30 seconds" and "agent has exited and will never write again" can look identical — every adapter has to find its own signal. The two real options:

  • Process liveness. Ask the OS whether any agent process still has the session file open. Reliable on macOS/Linux for agents that hold the file (Claude Code, Codex). Cheap — a single lsof-equivalent syscall per session per check.
  • Terminator entry. Some agents write a sentinel line to the JSONL on clean exit. When it's there, it's authoritative. When it isn't (crash, kill -9), fall back to liveness.

If neither works for a given adapter, the adapter collapses to a single "quiet" state and never reports Done automatically — the user can mark it done explicitly. The point isn't to be clever; it's to never lie. Unknown exists for exactly this case.

Event flow

// the whole runtime, in spirit
let (tx, rx) = broadcast::channel(1024);

for adapter in adapters {
    spawn(async move {
        adapter.watch(tx.clone()).await;   // notify(2) → SessionEvent
    });
}

loop {
    select! {
        evt = rx.recv()    => registry.apply(evt),      // dedupe + debounce
        key = keys.recv()  => ui.handle(key, &registry),
        _   = redraw_tick  => ui.render(&registry),
    }
}

Three primitives doing the work. broadcast::channel(1024) opens a fan-out queue: tx is the sender (cloneable, every adapter gets one and pushes events into the same stream), rx is the receiver the main loop reads from. spawn(...) hands an async block to the tokio runtime, which schedules it on a worker thread — one task per adapter, all running concurrently without blocking each other. The select! macro inside the loop awaits whichever input becomes ready first (a session event, a keypress, or a redraw tick) and reacts to it.

The result: no polling. The terminal redraws only when registry or input changes. On an idle fleet, Vigil costs nothing.

UI as a function of state

The UI is intentionally not imperative. The whole TUI layer is one pure function:

fn render(state: &AppState, area: Rect) -> Frame;

Given the same AppState, render produces the same screen — every time, no I/O, no globals, no time-of-day branches. The app loop's job is to compute the next AppState from incoming events; the UI's job is to translate that state into characters. Behavior and pixels are entirely separate concerns. The shape is borrowed from Elm and pure-React: state in, frame out.

This is a hard requirement, not a stylistic preference. The whole reason for it is testing:

// no tokio, no terminal, no event loop
let state = AppState::new(&[
    fixture::awaiting("claude-code", "~/code/api"),
    fixture::running("codex", "~/code/web"),
]);
let frame = render(&state, Rect::new(0, 0, 100, 30));
insta::assert_snapshot!(frame_to_text(&frame));

You construct a fake AppState, call render, and assert against a stored text snapshot. Layout regressions surface as a one-character diff in a checked-in file — the granularity you actually want for a TUI. The full app loop is exercised in a small handful of integration tests; everything else — every individual screen, every filter, every state-transition — runs without ever touching tokio or crossterm.

Stated as a rule: if a piece of UI needs the app loop running to test it, the design is wrong.

The hierarchy is: which need me → what are they doing → everything else. The default filter is awaiting. The default sort is "last activity, newest first." Two ways to act on a session:

  • Send a message inline (i to focus the input, type, ↵ to deliver). Vigil writes to the selected agent's stdin via the adapter — no context switch, no attach. Good for short responses: "yes", "approve", "use port 8080 instead".
  • Attach (⇧↵) when you need the full CLI — long edits, scrollback, deeper context. Vigil execs the agent's own resume command and you're back in your usual environment.

A footer row aggregates spend across every adapter that reports it — so the cost of having five agents at work is always one glance away.

Navigation is modal but cheap: ↵ drills into the selected session's preview, ⎋ or ← always backs out one level (input → preview → list), and q quits from anywhere. There is never more than one keypress between you and the main view.

Why crossterm (and not tmux)

The terminal-backend slot has four real candidates:

  • crossterm — pure Rust, cross-platform (macOS, Linux, Windows). Default for almost every ratatui app. What we'll use.
  • termion — Unix-only, simpler API. Smaller surface, but no Windows. Fine if portability isn't a goal.
  • termwiz — from the wezterm project. Richer features (true-color, sixel/image, more capability detection), heavier, less common.
  • pancurses — bindings to ncurses via FFI. Mature but pulls in a C dependency. Out of style for new Rust TUIs.

Tmux is a different layer of the stack — a terminal multiplexer that hosts panes and sessions inside one window. You could build a "vigil-as-tmux" using a shell script that opens one pane per agent and lets you cycle between them with the prefix key. It's a valid 50-line tool and it solves some of the problem.

What it doesn't do is the actual hard work: classifying state. Tmux gives you N panes and asks you to check each one yourself — which is exactly the manual attention-routing Vigil exists to replace. Tmux is a viewer; Vigil is a router. They're complementary (Vigil could even attach into a tmux pane), but neither substitutes for the other.

Validation prototype

The hardest part of Vigil is not the TUI — it's correctly answering "what state is this session in?" from a log file the user can't see being written. Before writing a single ratatui widget, we need to know we can answer that question well enough on real data. Three adapters at minimum — Claude Code, Codex, and Pi — so the trait shape is forced to generalize past any single agent's quirks before we commit to it.

The premise

State classification has two inputs: manual action from the user (typing into the agent, approving a tool, walking away) and a signal from the agent (a new line in the JSONL, a file closed, a permission prompt written). The validation question is: when the human does X, does the agent emit a signal Vigil can read, and does Vigil's classify() read it correctly?

That's a small enough question that we don't need a 30-session corpus to answer it. We need three sessions per adapter — one driven into each of the three states the UI actually depends on (Running, AwaitingInput, Idle) — and a test harness that captures the log at that moment and asks the classifier what it sees.

Approach

  1. Drive three sessions per adapter. For each of claude-code, codex, and pi: manually start a session and walk it into each target state. Ask it to run a tool (Running); ask it to do something that requires permission (AwaitingInput); finish a turn and wait 30s (Idle). At each target state, snapshot the session file. Total: 9 fixtures.
  2. Label. A tiny fixtures/labels.toml maps snapshot → expected SessionState + one-line justification. Anonymize message bodies before committing.
  3. Write classify(). Pure function in each adapter crate. Inputs: parsed tail of the log + filesystem signals (mtime, size delta, file-still-open). No async, no IO, no globals. Trivial to unit-test.
  4. Golden test. One #[test] per adapter: iterate the 3 snapshots, call classify, assert. On failure, print expected vs actual and the relevant log tail. Runs in CI on every commit.
  5. Live confirmation. A small cargo run --bin vigil-probe -- <adapter> mode that tails a real session and prints state transitions as they happen — so you can drive a live session, watch Vigil react, and confirm the classifier behaves under real-time conditions, not just on frozen logs.
  6. Grow the fixture set lazily. Every "Vigil got it wrong" in real use becomes the 10th, 11th, Nth fixture before the fix lands. The corpus grows out of failures, not upfront effort.

What this lets us decide

  • Whether the AgentAdapter trait shape (especially classify) is right — three real implementations force it to generalize.
  • Whether the SessionState enum has the right cardinality. We'll find out fast if Idle vs AwaitingInput is too coarse or Done vs Idle too fine.
  • How often Unknown happens in practice — and therefore how prominent the UI should make it.
  • Whether the prototype's confidence is high enough that any UI work is worth doing at all.

Only after the prototype clears the bar does any registry, notify wiring, or UI code get written.

Open questions

  • Classifier evolution. Beyond the prototype above, heuristics keep evolving from real-world use — every misclassification adds a fixture to the corpus.
  • Attach semantics. Each agent has different resume ergonomics. Claude Code supports --resume <id>; others may require launching a fresh shell in the right CWD. Adapters return a Command so each can do what fits.
  • Remote / multi-host. Out of scope for v1. The trait would extend cleanly later — adapters could read over SSH instead of from disk.
  • Audio cue. When any session transitions into AwaitingInput, play a single short tone — the same tone for every agent. The point is "come back and look," not "look at this specific agent"; the screen already says which one. Mute-all with one keypress. System notifications stay opt-in on top of that.
  • Cost telemetry. Surfaced as a daily aggregate in the status row (see mockup) — total spend and token count, with per-agent breakdown. v0 parses Claude Code's cost_usd field; per-session column lands once Codex's billing equivalent is wired in.

What I'm building first

  1. The Claude Code adapter + classifier, validated against a corpus of real local sessions.
  2. A minimal ratatui shell that renders the registry as a flat list with the filter row.
  3. Attach to a session via ⇧↵.
  4. Codex adapter (second proof the trait is right).
  5. Pi adapter (third proof — and the one whose log shape is least documented, which makes it the most useful pressure test).
  6. OpenCode adapter.

Everything else — preview pane, search, notifications — comes after those five work end-to-end.
