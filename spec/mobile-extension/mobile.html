1. Problem Statement

Vigil solves the attention-routing problem for a fleet of AI agents running in parallel. Today it solves it only when you're at your terminal. The moment you step away — lunch, a meeting, a commute — you're back to the pre-vigil world: agents sit blocked on permissions, you miss the window, the session goes cold.

The information vigil surfaces (who's waiting, what did they ask, should I approve?) is exactly the kind of low-latency, asynchronous signal that a phone is built for. A TUI is the right primary interface; a mobile companion is the right always-with-you interface.

Core insight: Vigil's value is attention routing. The terminal does it well when you're at a desk. Mobile extends that routing to everywhere else. The phone doesn't replace the TUI — it's the pager that tells you when to run back to the TUI, plus quick actions so you often don't have to.

2. User Story

You've kicked off eight Claude sessions across three repositories — a refactor, a spec, and a test suite. You walk away from your laptop to make coffee. Your phone buzzes.

"vigil — vast-babbage / claude-1 needs input: Run shell command? cargo test --workspace"

You tap Approve from the lock screen. Done. You didn't open a laptop. The session unblocks and continues. Three more agents finish while you're away. You see a summary when you get back.

That's the whole pitch.

3. Architecture

The Connectivity Problem

Vigil today is local-only: one binary, reads from ~/.claude/, writes nothing. Mobile requires a networked path from the phone to the session state on your laptop. There are two honest options:

Option How it works Pros Cons
A. Local-network relay vigil serve exposes an HTTP+WebSocket API on LAN. Phone connects via local IP or mDNS (vigil.local). No cloud dependency. Data never leaves local network. Zero auth complexity. Doesn't work away from home/office. No push notifications without a relay.
B. Tunnel relay (Tailscale / Cloudflare) vigil serve tunnels out via Tailscale or a WARP connector. Phone reaches it over VPN or public URL. Works anywhere. Secure by default (Tailscale ACLs). Minimal setup if user already runs Tailscale. Requires Tailscale account. Adds infra complexity. Not zero-setup.
Recommendation: Start with Option A (LAN mode) for v0. It gets 80% of the value (home/office context) with zero backend work. Design the API surface so Tailscale support drops in later as a transport flag: vigil serve --tailscale.

New Component: vigil-server

A new crate that wraps the existing SessionRegistry and exposes it over HTTP + WebSocket. The adapter pipeline is already decoupled from the TUI — vigil-server slots in as a second consumer of the same event stream, no changes to core logic.

EndpointDescription
GET /sessionsSnapshot of all containers with state, last message, repo, agent kind
WS /eventsReal-time stream of state-change events. Same event types as the TUI channel.
GET /sessions/:id/logPaginated recent log for a container. Cursor-based.
POST /sessions/:id/messageSend a freeform message to the session stdin (same path as TUI send)
POST /sessions/:id/respondShortcut: respond to the current awaiting prompt. Body: {"action": "approve"|"deny"}
GET /healthLiveness check with version + uptime

Mobile App: PWA vs Native

Two realistic options for the client:

Progressive Web App (PWA)React Native
Push notifications Web Push API — works on Android, limited on iOS (requires iOS 16.4+, home screen install) Native APNs / FCM — full support
Distribution No app store. Self-hosted or served directly from vigil serve. App store or TestFlight. Higher friction.
Dev effort Low — one codebase, no native toolchain Medium — native bridge, two build pipelines
Offline support Service worker caching — good enough for shell + last snapshot Full SQLite local store if needed
Recommendation: PWA first. Vigil's audience (developers) is comfortable adding a web app to their home screen. The lack of native push on older iOS is a real constraint but acceptable for v0. If push becomes a hard requirement, ship a minimal Expo / React Native wrapper that embeds the same web UI.

Design notes

Sessions grouped by urgency, not by repo — the most critical information surfaces first. Within each group, sorted by recency.

State indicators mirror the TUI color vocabulary: red for awaiting, gold for running, gray for idle/done. Pulsing dots on awaiting.

Pull-to-refresh triggers a full snapshot re-fetch. The WebSocket keeps the list live; pull-to-refresh is a fallback.

Swipe actions:

  • Swipe right on awaiting row → quick approve
  • Swipe left on any row → archive/dismiss

Long press opens a context menu: view log, send message, archive.

Design notes

The log view is read-heavy. Mobile constraints (no mouse, small screen) mean we sacrifice some density for readability: larger line height, fewer turns visible at once.

Sticky permission banner at the bottom when state is AwaitingInput. Shows the permission type and command inline with approve/deny CTAs.

Scroll to bottom on open; user can scroll up to read history.

Composer switches to a full-height text input when tapped, with a send button. Supports multiline. Return = newline, send button = submit.

Turn numbers double as jump targets — tap a turn number to copy the turn link.

Notification design

The permission notification is the highest-value interaction. It must work from the lock screen, with zero app opens required for a simple approve.

Three actions on every AwaitingInput notification:

  • Approve — sends the affirmative response and dismisses
  • Deny — sends the negative response and dismisses
  • View — opens vigil to the log view for that session

Non-awaiting events (done, error) deliver a simple informational notification with a single "View" action.

Notification grouping: one notification per session, updated in-place. Not a new notification per event — that would be overwhelming on a busy fleet.

Quiet hours: user can configure a time window during which only Error events bypass DND.

4.4 Settings

Minimal. Three sections:

  1. Connection — host address, port, connection status indicator, QR-code pairing flow
  2. Notifications — which states trigger push (awaiting, done, error), quiet hours, per-repo filters
  3. Display — dark/light (default: match system), log density (compact/comfortable)

5. Notifications Deep Dive

Delivery path

Push notifications require a push service. On iOS, that's APNs. The challenge: vigil-server is on your laptop, not in the cloud. Bridging that gap honestly:

OptionMechanismNotes
WebSocket background keep-alive PWA holds a persistent WS connection. Background sync API delivers events when app is backgrounded. Least reliable on iOS (background suspension). Good enough on Android with Web Push.
Web Push API vigil-server sends push payloads to browser's push service (FCM for Chrome/Android). No third-party relay needed. Works on Android Chrome natively. iOS Safari support via Web Push (iOS 16.4+). Solid for PWA.
Vigil relay service Optional hosted relay at relay.vigil.dev. laptop tunnels events to relay; relay pushes to APNs/FCM. Enables native push on all iOS versions and from any network. Requires running a server. Privacy tradeoff (relay sees event metadata but not log content).
Privacy note: If a relay service is built, it MUST be opt-in and transparent. Relay should only receive: session ID, session state, repo name, and the permission prompt type — never full log content. Users running sensitive workloads should always have a fully local option.

Notification taxonomy

7. Non-Goals

  • Running agent sessions directly on mobile (vigil observes; agents live on laptop/server)
  • A full-featured code editor or file browser
  • Multi-user / team features — this is a personal tool
  • Android-first: design for iOS first, ensure nothing breaks on Android
  • Offline mode beyond the last-fetched snapshot
  • Exposing vigil-server to the public internet without explicit user action

8. Phased Roadmap

Milestone 1 — Foundation
vigil-server + web UI shell
New vigil-server crate with REST + WebSocket API. Minimal PWA that connects over LAN and shows a live session list. No notifications yet. QR pairing. Validates the architecture before investing in polish.
Milestone 2 — Core flows
Log view + send message + notifications
Log viewer with turn-based rendering. Composer for freeform messages. Approve/deny inline for AwaitingInput sessions. Web Push notifications on Android. iOS push via Web Push on home-screen-installed PWA (iOS 16.4+).
Milestone 3 — Reliability & reach
Tailscale support + notification polish
vigil serve --tailscale flag for remote access. Notification grouping, quiet hours, per-repo filters. Activity feed. Swipe actions on session rows.
Milestone 4 — Nice-to-haves
Relay service + widgets + watch
Optional hosted relay for users without Tailscale. iOS home screen widget showing "N awaiting" count. Explore Apple Watch complications. Cost/token dashboard.

9. Open Questions

Q1: Security model for vigil-server

The API endpoint can send messages to agents. Even on LAN, this is sensitive. Should vigil-server require a token (generated at startup, shown in QR code)? How do we handle multiple devices?

Q2: Which push path for iOS?

Web Push on iOS requires the PWA to be installed to the home screen. Is that acceptable for v0, or should we ship a thin React Native wrapper from day one to get reliable APNs support?

Q3: "Approve" semantics across adapters

For Claude, "approve" = sending "y\n" to stdin on a permission prompt. How does this generalise to Pi, Codex, OpenCode? Each adapter needs an respond(action) method alongside attach_command().

Q4: What to show when log is large?

Some Claude sessions have hundreds of turns. Loading the full log on mobile is slow and noisy. Should the log view default to the last N turns and require explicit "load more"?

Q5: vigil-server lifecycle

Should vigil serve be a separate command, or should the existing vigil TUI optionally spin up the server in the background? The latter is more convenient but blurs responsibilities.
